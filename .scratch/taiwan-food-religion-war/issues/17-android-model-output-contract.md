# 17 — 讓中階 Android 的端側裁決真的產出結果

**What to build:** 玩家在目標級距的 Android 手機（非旗艦，如 Pixel 8a）上使用已安裝的小模型時，端側裁決要能實際產出通過驗證的結果，而不是每次都退到備援。

**Blocked by:** 12 — 完成原生裝置人工驗收.

**Status:** ready-for-human

- [ ] 在 Pixel 8a 或同級距裝置上，以至少一顆推薦模型取得通過驗證的模型裁決（`isFallback` 為 `false`、不顯示備援揭露）。
- [ ] 不放寬任何安全或內容驗證規則；壞輸出仍必須退到備援。
- [ ] iOS 既有的模型裁決行為不得回歸。

## Comments

- 2026-08-11 由 ticket 12 的 Android 實機驗收拆出。**現況**：逾時已不是限制（40 秒門檻下 1B 模型 16.6 秒完成），但 `gemma-3-1b` 與 `gemma-3-270m` 都把 prompt 中 `"verdict":"信仰堅定|勉強護教|叛教邊緣"` 整串抄成 verdict 值，並把 JSON 包在 ```json code fence 裡，因此一律以 `parse` 失敗退到備援。真機日誌證據見 ticket 12。
- 兩個當時提出的解法都被明確否決，本票不預設採用其中任何一個：
  1. **寬鬆的 JSON 擷取**（從輸出取出第一個完整 JSON object，忽略 code fence 與前後說明）—— 使用者決定不放寬解析。
  2. **改寫 prompt 的輸出契約**（三個合法值改成規則列、範例物件放具體值而非豎線串）—— 使用者決定不動 prompt，因為 iOS 上模型生成吐槽已驗收正常，改動有回歸風險。
- 第三條未評估的路：為 Android 指定不同的推薦模型（例如 4B），或針對 Android 提供不同的輸出契約。需要先量測 4B 在中階機上的速度與輸出品質。
- 這不是阻斷性缺陷 —— 備援透明且遊戲可完成 —— 但它讓 `spec.md:44`（story 29，端側個人化裁決）在 Android 上實質未達成，因此獨立追蹤而不是留在已知限制裡消失。
