# Twinkle AI「台灣食物宗教戰爭」規格 v2.0

- Status: `ready-for-agent`
- 產品：Twinkle AI - Little Star App
- 功能模組：`iPlayground` 獨立遊戲 Feature
- 規格日期：2026-08-06
- 取代：`Twinkle_AI_Food_Religion_War_Spec_v1.0.md` 的跨主題淘汰賽玩法，以及本目錄既有 01–05 tickets 對該玩法的描述

本文件是「台灣食物宗教戰爭」的權威產品規格。舊 spec 與既有 tickets 僅保留歷史脈絡；若玩法、名詞、流程、視覺或驗收條件有衝突，一律以本文件、`CONTEXT.md` 與相關 Accepted ADR 為準。後續 `/to-tickets` 必須依本文件重新拆票，不得沿用舊淘汰賽 acceptance criteria。

## Problem Statement

Little Star App 需要一個範圍清楚、數十秒可完成、能展示端側 LLM 價值的互動功能。現有版本雖然有明確的開始、選擇、辯護與結果，卻把粽子與香菜等互不相干的偏好放入跨主題淘汰流程，使玩家的選擇看似彼此擊敗，最後只留下單一最高位階立場。這不符合玩家真正表達的多項飲食偏好，也讓結果語意失真。

現有視覺與模型入口也需要一起收斂：遊戲要有可辨識的台灣夜市氣氛，但不能讓密集裝飾壓過角色、選擇與辯護；缺少本機模型時，提醒必須可見但不能暗示下載是開始遊戲的前置條件。手機與寬螢幕必須呈現同一套資訊順序、狀態與操作語意。

## Solution

玩家從 Home 直接進入一局四次獨立「飲食抉擇」。每題從同一飲食主題的一對「飲食立場」中選一項，選定後立即鎖定並加入四項「本局信仰清單」；任何立場都不會因後續題目被淘汰或取得高低排名。

四題完成後，遊戲先完整顯示本局信仰清單，再由玩家觸發一次不可重抽的「辯護抽籤」。抽籤只會從這四項已選立場中抽出一項。系統明確呈現抽中結果與固定質疑，玩家以最多 50 個使用者可見字元辯護；已安裝的端側模型產生三級裁決與安全吐槽，沒有可用模型或生成失敗時則透明使用備援裁決。結果頁以本次抽中的立場為主要內容，同時保留完整信仰清單，並固定顯示「本次抽中；四個選擇都會保留。」

介面採已核准的 Variant A「招牌擂台」：單一紅色主招牌、兩顆可見燈泡、深色油布／金屬面板，以及只用於當前左右席位的紅／青提示。手機將同一組語意單元垂直排列，寬螢幕將其左右排列。無模型時，每次 App run 只出現一次提醒，主要行動為「先玩再說」，次要行動為「前往推薦模型」。

## User Stories

1. As a Little Star App 使用者, I want to 在 Home 看見「台灣食物宗教戰爭」入口, so that 我能快速開始一局。
2. As a 玩家, I want to 點擊入口後直接開始第一個飲食抉擇, so that 我不必先讀教學或下載模型。
3. As a 玩家, I want to 知道一局包含四個獨立選擇與一次辯護抽籤, so that 我能正確理解遊戲流程。
4. As a 玩家, I want to 每題只比較同一飲食主題的兩個立場, so that 選擇具有一致且合理的語意。
5. As a 玩家, I want to 每局遇到六組題庫中的四組不同題目, so that 重玩時有變化。
6. As a 玩家, I want to 每局的四組題目順序隨機, so that 流程不會每次完全相同。
7. As a 玩家, I want to 點擊整張立場卡完成選擇, so that 手機操作簡單且觸控目標清楚。
8. As a 玩家, I want to 在立場卡上優先看見角色與立場名稱, so that 我能快速辨識選項。
9. As a 玩家, I want to 選定後看見文字、勾選、邊框與亮燈回饋, so that 我不必只靠顏色判斷狀態。
10. As a 玩家, I want to 選定後兩張卡立即鎖定, so that 快速連點不會改變已記錄的選擇。
11. As a 玩家, I want to 看見「立場已記錄」回饋, so that 我知道選擇已加入本局信仰清單。
12. As a 玩家, I want to 在短暫回饋後自動進入下一題, so that 節奏流暢。
13. As a 玩家, I want to 看見 1–4 的飲食抉擇進度, so that 我知道還有幾題。
14. As a 玩家, I want to 四次選擇都保留在本局信仰清單, so that 每項偏好都有被記住。
15. As a 玩家, I want to 四題完成後先檢視完整信仰清單, so that 我能確認抽籤候選只來自自己的選擇。
16. As a 玩家, I want to 主動按下抽籤行動後才揭曉辯護題目, so that 抽籤是清楚且有期待感的獨立節拍。
17. As a 玩家, I want to 抽籤只從本局信仰清單選一項, so that 我不會被要求替未選的立場辯護。
18. As a 玩家, I want to 一局只能抽一次且不能重抽, so that 驚喜與挑戰具有可信度。
19. As a 重玩玩家, I want to 候選允許時避免連續兩局抽中同一立場, so that 重玩較有變化。
20. As a 玩家, I want to 抽籤結果明確標出是哪一項被抽中, so that 我知道接下來要替誰辯護。
21. As a 玩家, I want to 結果文案說明四個選擇都會保留, so that 我不會誤認其他選擇已失效。
22. As a 玩家, I want to 看見與抽中立場相符的固定質疑, so that 我知道辯護題目。
23. As a 玩家, I want to 固定質疑幽默但公平, so that 遊戲有火花而不曲解我的立場。
24. As a 玩家, I want to 自由輸入 1–50 個使用者可見字元的辯護, so that AI 能回應我的實際理由。
25. As a 玩家, I want to 看見目前字數與就地驗證, so that 我能修正空白或過長內容。
26. As a 玩家, I want to 送出後鎖定模型、輸入與送出行動, so that 裁決只啟動一次。
27. As a 玩家, I want to 裁決期間看見遊戲內等待狀態, so that 我知道系統仍在處理。
28. As a 玩家, I want to 一次看見完整三級裁決與一句吐槽, so that 結果不會呈現半成品。
29. As a 玩家, I want to AI 回應抽中立場、固定質疑與我的實際辯護, so that 端側模型價值清楚可感。
30. As a 玩家, I want to 吐槽只針對食物、立場或論點, so that 遊戲有趣但不攻擊我或任何群體。
31. As a 玩家, I want to 沒有模型時仍能完成整局, so that 前面的選擇不會白費。
32. As a 玩家, I want to 模型載入、生成、解析、驗證或逾時失敗時自動得到備援結果, so that 遊戲不會卡住。
33. As a 玩家, I want to 清楚知道目前使用備援裁決, so that 固定文案不會被假裝成個人化 AI 回應。
34. As a 玩家, I want to 不看見底層錯誤、例外或模型技術細節, so that 遊戲體驗保持一致。
35. As a 未安裝模型的玩家, I want to 每次 App run 只被提醒一次, so that 入口可被發現但不會反覆打斷遊戲。
36. As a 未安裝模型的玩家, I want to 以「先玩再說」關閉提醒並繼續, so that 我知道下載不是必要條件。
37. As a 想使用 AI 的玩家, I want to 從提醒或辯護頁前往推薦模型區, so that 我能沿用既有模型管理能力。
38. As a 前往模型管理的玩家, I want to 返回遊戲後保留進度並重新偵測模型, so that 下載或取消後不用重玩。
39. As a 玩家, I want to 模型下載失敗時仍能繼續遊戲, so that 外部失敗不阻斷核心流程。
40. As a 玩家, I want to 在辯護送出前切換已安裝模型, so that 我能選擇此次裁決使用的端側模型。
41. As a 玩家, I want to 每個新 Session 重新套用穩定且可預期的預設模型, so that 上一局選擇不會暗中延續。
42. As a 手機玩家, I want to 以標頭、進度、主要任務、次要情境／模型入口的順序操作, so that 小螢幕資訊層級清楚。
43. As a 寬螢幕玩家, I want to 看見與手機相同語意單元的左右配置, so that 換尺寸後仍是同一套遊戲。
44. As a 玩家, I want to 看到精簡但可辨識的台灣夜市風格, so that 遊戲有地方感而不被裝飾干擾。
45. As a 減少動態效果使用者, I want to 以靜態標記與淡入取代跳動或閃爍, so that 我仍能理解所有狀態變化。
46. As a 螢幕閱讀器使用者, I want to 聽見進度、選擇、鎖定、抽籤、質疑、字數、等待、裁決與操作語意, so that 我能獨立完成遊戲。
47. As a 不辨色玩家, I want to 狀態不只由紅、青或琥珀色表示, so that 我能可靠辨識目前狀態。
48. As a 玩家, I want to 在遊戲中返回時先確認是否離開, so that 我不會誤觸失去本局進度。
49. As a 玩家, I want to 以「再玩一次」快速開始新 Session, so that 我能體驗不同題目與抽籤結果。
50. As a 玩家, I want to 以「回首頁」離開並清除本局, so that 下次進入從一致狀態開始。
51. As a 產品展示者, I want to 離線或模型異常時仍可完整展示, so that Demo 不依賴單次推論成功。
52. As a 內容維護者, I want to 集中管理立場組合、固定質疑、角色識別、備援文案與安全護欄, so that 調整內容不改動流程語意。
53. As a 測試者, I want to 從玩家可觀察的最高層流程驗證整局, so that 測試不依賴 Widget 階層或狀態類別名稱。

## Implementation Decisions

### 權威流程與狀態

- 舊的跨主題淘汰流程已被完整取代，不是改名或換文案。新的合法流程為：建立本局題目 → 四個飲食抉擇 → 完整本局信仰清單 → 等待玩家觸發辯護抽籤 → 顯示抽中立場 → 辯護 → 裁決中 → 結果。
- 四個飲食抉擇彼此獨立；後一題不能淘汰、覆蓋、排名或晉升前一題的選擇。`VS` 只可出現在同一題的兩個可比較立場之間。
- 玩家選定立場後立即鎖定整題，只接受第一個有效輸入。短暫記錄回饋結束後才前進。
- 四題完成後必須保留一個明確的 pre-defense draw beat：先展示完整本局信仰清單，再提供抽籤行動，最後才揭曉抽中立場；不得自動跳過此節拍。
- 辯護抽籤只以四項本局信仰清單為候選、每局只執行一次且不可重抽。同一次 App run 中，若本局另有候選，避免與上一局抽中相同飲食立場。
- 結果頁主要呈現抽中立場的大型角色、名稱、抽中標記、固定質疑、裁決與主要行動；完整四項本局信仰清單以次要層級保留，抽中項目在原位置標記。
- 結果 guardrail 固定為「本次抽中；四個選擇都會保留。」遊戲 UI 不得以舊的最高位階用語描述或否定結果。
- 「再玩一次」建立乾淨的新 Session 並回到第一個飲食抉擇；「回首頁」清除本局並返回 Home。中途返回仍須確認離開。

### 立場題庫與內容

- 第一版「立場題庫」固定為六組：北部粽派／南部粽派、香菜加爆派／香菜退散派、豆花配糖水／豆花配豆漿、火鍋沾沙茶／火鍋原湯派、珍奶全糖／珍奶微糖、薯條加鹽／原味不加鹽。
- 每局從六組中隨機抽出四組不同題目，再隨機排序；不得在同一局重複題目。本規格不額外指定抽樣權重。
- 十二個飲食立場都必須有穩定識別、顯示名稱、所屬比較主題、角色資產識別、幽默但公平的固定質疑，以及安全備援裁決內容。
- 現有四個透明 Q 版角色資產保留；其餘八個角色沿用相同視覺風格、透明背景、完整角色與一致留白。所有必要文字由原生 UI 呈現，不烘焙進圖片。
- 不計算總分、偏好排名或人格類型，也不將四項選擇合成單一身份。

### 視覺、響應式與互動

- Variant A「招牌擂台」是 production design basis。Variant B 只保留為寬螢幕密度參考；Variant C 已拒絕，不得採用帳冊式資訊架構。
- 夜市識別使用單一紅色主招牌、兩顆可見燈泡、深色油布／金屬面板與溫暖琥珀回饋。不得加入裝飾側招牌、棚架、懸掛燈串、攤販器具、凳子、廟宇屋頂、舞台燈或背景生成文字。
- 紅／青只代表當前兩個選擇席位，可跨題重用；飲食立場的身份必須由文字與角色表達。琥珀只用於目前步驟、已記錄選擇、抽中標記與主要行動。
- 手機與寬螢幕共用相同語意順序：遊戲標頭 → 進度 → 主要任務 → 次要情境／模型入口。手機垂直堆疊，寬螢幕將相同單元左右排列，不得為不同尺寸建立不同流程。
- 每張立場卡整張可點，且角色與立場名稱優先。已選狀態同時提供文字、勾選、邊框與照明；任何必要資訊不得只靠顏色或動效。
- 一般動效只使用短促的招牌亮燈、選擇記錄與抽籤揭曉回饋；手機可使用輕觸覺，不加入音效。系統要求減少動態效果時，以靜態標記與淡入式說明取代明顯移動、跳動或閃爍。
- 430 × 932 手機與 1280 × 900 寬螢幕是 prototype 已驗證基準；production 仍須覆蓋專案支援的最小與最大手機、鍵盤 inset、文字縮放與螢幕閱讀器。

### 模型提醒、選擇與導覽

- 沒有可用模型時，每次 App run 只顯示一次「AI 評審還沒來報到」提醒。提醒必須同時表達「不影響遊戲」。
- 提醒的主要行動固定為「先玩再說」，次要行動固定為「前往推薦模型」；下載不得成為進入或完成遊戲的必要條件。
- 關閉提醒後，本次 App run 不重複顯示；辯護頁仍保留可見但不搶過固定質疑與輸入的模型下載卡。
- 模型入口導向既有模型管理頁的推薦模型區，不新建下載、管理或模型狀態頁。離開遊戲前往模型管理時保留本局；返回後重新發現模型。下載取消或失敗不阻斷遊戲，技術錯誤不進入遊戲 UI。
- 辯護頁列出可發現的已安裝 GGUF 與 MLX 模型。預設選擇可重現：GGUF 優先於 MLX，同類模型依穩定排序取第一個。
- 玩家可在送出辯護前切換模型；送出後模型選擇、輸入欄與送出行動一併鎖定。模型選擇只存在目前 Session，新 Session 重新發現並套用預設。
- 遊戲 Feature 只依賴既有高層 inference abstraction、generation boundary 與可替換的裁決服務，不直接依賴 FFI、Pigeon 或特定 backend。

### 辯護、裁決與安全

- 玩家以 1–50 個使用者可見字元自由辯護；去除首尾空白後不得為空。顯示即時字數，空白或超限時就地說明且不能送出。
- 模型每次辯護最多呼叫一次。輸入至少包含抽中立場、對應固定質疑、玩家原始辯護、三級裁決準則與安全護欄。
- 模型結果必須包含一個合法三級裁決與一句安全短吐槽；完成並驗證後一次顯示，不在遊戲 UI 逐字串流，不顯示 Markdown、前後說明或技術資訊。
- 三級裁決固定為「信仰堅定／勉強護教／叛教邊緣」。明確倒向相對立場或否定抽中立場時不得判為「信仰堅定」。
- 吐槽只可針對食物、飲食立場或論點漏洞，不得羞辱玩家、推測人格或智力、攻擊地區／族群／文化／信仰，也不得重述或擴大玩家輸入的不安全內容。
- 沒有模型、所選模型消失、載入或生成失敗、40 秒逾時、輸出無法解析、缺欄位、非法裁決或內容驗證失敗時，自動產生與抽中立場相符的安全備援裁決並透明揭露。（門檻原訂 20 秒，2026-08-11 依實機量測調整；見下方「逾時門檻」。）
- 成功、逾時、失敗或取消接近同時發生時，只接受第一個合法終態；後續事件不得覆寫結果，底層 Session 與 native 資源必須正確取消及釋放。

## Testing Decisions

- 好的測試只驗證玩家可觀察行為與已公布契約，不檢查 Widget 階層、狀態管理類別名稱、私有欄位、亂數實作、prompt 拼接或 native bridge 細節。
- 主要且最高的測試接縫只有一個：從 Home 進入真實遊戲 Feature 的高層 Widget flow，透過可控亂數來源與可替換裁決服務，完成四次飲食抉擇、pre-defense draw beat、辯護、裁決、結果、重玩與離開。
- 可控亂數是 domain boundary：測試可指定四組題目、題序、抽中立場與跨局去重情境；production 亂數分布本身不以脆弱的統計測試驗證。
- 可替換裁決服務是 inference boundary：自動測試模擬模型發現、選擇、成功、逾時、無效輸出與失敗，不載入真實模型、不呼叫網路，也不跨越既有 `InferenceSession`／`GenerationController` 邊界。
- 沿用既有 `food_religion_game_flow_test`、`food_religion_defense_flow_test`、`food_religion_ai_flow_test`、`food_religion_character_feedback_test` 與 `food_religion_accessibility_test` 的玩家可觀察 Widget flow prior art；舊測試中的準決賽、決賽、晉級與最高位階斷言必須刪除或改寫，不能只新增新版測試讓矛盾共存。
- 核心流程覆蓋：四組題目不重複且順序可控；每題只接受第一個選擇；四項選擇皆保留；抽籤前先顯示完整清單；抽籤只來自清單且不可重抽；跨局候選允許時避開上一局相同立場。
- 結果覆蓋：抽中立場保持主要層級；完整清單仍可見且抽中項原位標記；固定顯示「本次抽中；四個選擇都會保留。」；任何玩家可見狀態都不出現舊流程詞彙或暗示立場有高低排名。
- 模型提醒覆蓋：無模型時每個 App run 只顯示一次；「先玩再說」是主要行動且不中斷流程；辯護頁入口持續存在；往返模型管理保留本局並重新發現模型；下載失敗不洩漏技術錯誤。
- 辯護與裁決覆蓋：1 與 50 個使用者可見字元可送出，空白與 51 字不可送；只提交一次；合法 AI 結果、所有失敗分類、備援揭露與終態競態皆產生唯一結果。
- 視覺與無障礙自動驗收覆蓋最小／最大手機、430 × 932、1280 × 900、鍵盤 inset、文字縮放、reduced motion 與 semantics；確認無水平 overflow、整卡觸控、狀態不只靠顏色，以及手機／寬螢幕語意順序一致。
- 真實模型品質、40 秒完成率、觸覺感受、VoiceOver、TalkBack 與實機返回手勢保留為人工裝置驗收；它們不由假模型或純 Widget 測試宣稱完成。
